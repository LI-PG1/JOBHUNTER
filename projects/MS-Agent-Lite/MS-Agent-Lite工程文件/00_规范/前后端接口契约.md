# 前后端接口契约（需求-开发-落地闭环）

> **定位**：本文件是前端（`20_执行/web/app.js`）与后端（`20_执行/server.js`）之间全部 API 的**唯一契约**，用于保证"前端业务需求 → 后端接口实现 → 功能落地"的闭环可核对、可回归。
> **闭环原则**：前端每个功能点必须有后端接口支撑；后端每个接口必须有前端调用点；契约变更必须同步更新本文件与两端代码。
> 本文件由 2026-08 全量盘点生成（前端 19 个调用点、后端 17 个端点 + 1 个预览路由），盘点结论：**前端调用的所有端点后端均已实现，无缺失**；盘点发现并修复的缺口见文末"闭环修复记录"。

## 二、接口明细

### 2.1 Provider 管理（1~4）

**GET `/api/providers`**
- 响应：`{ providers: [{ name, model, baseUrl, displayName?, apiKeyMasked, enabled, cap[], maxOutputTokens?, hasKey }] }`
- 说明：`apiKey` 永不下发（仅掩码）；`displayName` 用于前端日志/状态条/自检条显示「显示名 (模型名)」；`hasKey` 用于前端"有无可用 Key"判定；config.json 不存在时返回空数组（分发适配）。

**POST `/api/providers`**
- 请求：`{ name, baseUrl, model, apiKey?, cap?: string[], enabled?: boolean, maxOutputTokens?, displayName? }`
- 响应：`{ providers: [...] }`（保存后的全量列表）
- 语义：name 存在则更新（apiKey 缺省/空保留原值），不存在则新增；保存后写盘 config.json。

**POST `/api/providers/:name/test`**
- 请求：`{}`（仅配置校验）或 `{"real":true}`（真实最小请求）
- 响应：`{ ok, detail?, error? }`（实际还返回 `name/model/baseUrl/enabled/hasKey/caps/mode` 等内部字段，前端仅使用 `ok/detail/error`）

**DELETE `/api/providers/:name`**
- 响应：`{ providers: [...] }`

### 2.2 数据读取（5~8）

**GET `/api/companies`** → `{ companies: string[] }`（扫描 `30_产出/面试材料/` 内任意 `.html` 得到的岗位名历史；前端岗位名称已改为纯文本输入，本端点保留供扩展/CLI 使用）

**GET `/api/search-zones`** → `{ zones: [{ id, name, sites: string[] }] }`

**POST `/api/parse-resume`**
- 请求：`{ resumeFile: "data:...;base64,....", resumeExt: "pdf|docx|txt|md" }`
- 响应：`{ text, meta: { ext, size, lines, suspectedScan? } }`；失败 `{ ok:false, error }`
- 错误语义：`ext` 为 doc 时返回友好引导（另存为 docx/txt）；未知格式返回支持列表；pdf 提取文本过短时 `meta.suspectedScan=true`（疑似扫描件，前端展示引导）。

**POST `/api/fetch-jd`**
- 请求：`{ url }`
- 响应：`{ ok:true, text, from }` 或 `{ ok:false, error }`（"信息读取失败：…建议直接粘贴 JD 文本"）

### 2.3 任务（9~13）

**POST `/api/material`**（创建生成任务，立即返回 taskId，后台异步执行）
- 请求：`{ company(必填,≤80字,禁路径字符), resumeFile: dataUrl(必填), resumeExt?, jdText?|jdUrl?(至少其一), urls?: string[](≤15 条), refInfo?: string(≤20000 字), contact?: string(≤200 字), resumeVer?: "A"|"B"|""(后端保留，前端未暴露), resumeText?(内部回写，供 retry 复用，前端不直接提交) }`
- 响应：`{ taskId }`；校验失败 400 `{ error }`
- 后台流水线（与前端第 2 步输入一一对应）：解析上传简历 → JD 读取（URL 时）→ 参考网址逐条读取（失败跳过）→ runGenerate（8 文件）→ build → verify → check → done
- **本次修复**：解析出的 resumeText / 抓取到的 jdText 会**回写任务 input**，保证 retry 时上下文不丢。
- **补充参考信息**：`refInfo`（可选，≤20000 字）整块注入生成上下文【用户补充的参考信息】段（含"仅作参考、禁止照搬为候选人经历"约束）；`jdText`/`refInfo` 超长不拒绝、由流水线统一截断至 20000 字并标注"完整内容见 _上下文快照.md"（与前端提示一致）；retry 透传不丢。
- **联系方式**：`contact`（可选，≤200 字）写入生成材料开头（顶栏）与结尾（页脚卡片），联系方式变更触发重建（contentHash 纳入 contact）。
- **联网搜索（v0.4.9）**：配置了 `/api/web-search` 的 Tavily Key 时，生成前自动搜索"公司+岗位"权威来源并注入【联网搜索资料】上下文区块，搜索结果回写任务 input 的 `searchInfo`（retry 复用，不重复联网）；未配置则跳过，AI 按【联网核实协议】标注【待联网核实】。

**GET `/api/task/:id`** → `{ taskId, state, files:[{name,status,bytes,error}], result, log }`

**GET `/api/task/:id/events`**（SSE）
- 事件类型与字段：
  - `step`：`{name: pending|parsing|fetching|generating|building|verifying|checking|cancelled|error, status, detail?}`
  - `file`：`{name, status: running|done|failed, bytes?, error?}`
  - `log`：`{text}`
  - `build` / `verify`：`{ok, detail?}`
  - `check`：`{ok, output?}`（本次补充：retry 后也推送）
  - `done`：`{ok, build, verify, check, checkOutput, needsVerify, previewUrl, resultPath}`（v0.2.0 新增 `resultPath`：结果文件完整保存路径，前端生成成功后弹窗提示；v0.4.9 新增 `needsVerify: [{file, items[]}]`：生成文件标注的【待联网核实】时效信息汇总清单，前端结果页提示人工核对）
  - `needs-verify`：`{needsVerify: [{file, items[]}]}`（v0.4.9 代码审查补充：仅 retry-file 成功后推送——重跑清单刷新结果区，可能新增/清除【待联网核实】项）
  - `error`：`{text}`
- 机制：`retry: 2000` 自动重连；新连接重放全部历史事件；终态主动关闭。
- 说明：`build`/`verify`/`check`/`needs-verify` 事件**仅在 retry-file 成功后推送**；主生成流程以 `step`（building/verifying/checking）+ `done` 事件承载，`done` 内含 `build/verify/check/checkOutput` 汇总。
- 徽章复位（v0.4.9 代码审查）：联网搜索与文件生成共用 `fetching`/`generating` 步骤名，搜索结束后管线补发一次 `generating running`，避免前端徽章在生成期错显「读取网址…」。

**POST `/api/task/:id/cancel`** → `{ok:true}`（AbortController 中止）；任务已到终态时返回 409 `{ error: "任务已结束，无法取消" }`

**POST `/api/task/:id/retry-file`**
- 请求：`{ name }`（FILES 中的文件名）
- 响应：成功 `{ ok:true, build, verify, check, needsVerify }`（v0.4.9 代码审查补充 `needsVerify`：重试后重跑的【待联网核实】清单，前端可按此更新展示）；失败 `{ ok:false, error }`（`bytes` 仅在失败分支透传内部结果时可能携带）
- **本次增强**：重试成功（ok:true）后自动补跑 build + verify + check，并推送 `build`/`verify`/`check` 事件与汇总 log——保证"重试后 HTML 产物同步更新"（原实现只重生成 md，HTML 是旧的）。
- **v0.4.9 代码审查补充**：重试成功后再重跑 `collectVerifyItems` 并推送 `needs-verify` 事件——重试文件可能新增/清除【待联网核实】标记，保证结果区清单与产物一致。

**GET `/api/task/:id`（M3 质量回路扩展）**
- 响应在原有基础上增加 `quality` 字段：优先取 `result.qualitySummary`（完整轮次记录 `[{file, round, verdict, issues[]}]`）；无汇总时按各文件 `.quality.json` 聚合 `[{file, verdict, issues}]`。
- `quality` 与 `verify` 的 SOP-07 检查点互相对照：质检裁决与 verify 徽标同源（`PASS` / `WARN` / `FAIL`）。

**POST `/api/task/:id/rework-file`（M3 质量回炉）**
- 请求：`{ name, quality: { mode?, maxRounds?, reviewFiles? }, input?: { quality } }`（`name` 为需重做的文件名）
- 语义：强制单文件回炉——携带质检明细（D1~D5 issues）重写该文件（不走失败重试分支），完成后自动 rebuild + verify + check，并推送 `log`/`build`/`verify`/`check`/`needs-verify` 事件与汇总。
- 响应：成功 `{ ok:true, build, verify, check, needsVerify }`；失败 `{ ok:false, error }`。
- 并发：同一公司有在跑任务时返回 409 `{ error: "该公司已有任务进行中，请稍后再试" }`（与 `/api/material` 同锁）。
- 与 `retry-file` 的区别：`retry-file` 面向生成失败文件；`rework-file` 面向**生成成功但质检未过**的文件（质量回路 `warn-only` 模式下由用户手动触发，`on` 模式下自动进入下一轮，不落地前端）。

### 2.4 预览（14）

**GET `/preview/<岗位>/<岗位>面试准备.html`**：读取 `30_产出/面试材料/<岗位>/` 内 HTML；已做路径穿越防护（resolve + startsWith）；固定名不存在时回退目录内第一个 `.html`（产物重命名容错）。

### 2.5 本地能力状态（15~17，设置抽屉状态卡）

**GET `/api/cli-tools`** → `{ tools: [{ role, bin, found, ... }] }`：探测本机文档解析 / 图片识别命令行工具（可选用增强，缺失不阻塞主流程）。

**GET `/api/ocr-engine`** → `{ engine: { det, rec, dict, ready, ... } }`：内置离线图片文字识别引擎（模型随仓库打包）就绪状态。

**POST `/api/ocr`**：请求 `{ dataUrl }`（图片 data URL）→ 临时文件 → 三级回退（内置识别 → 本机工具 → 视觉模型）→ 返回识别文本，完成后清理临时文件。

### 2.6 联网搜索配置（18，设置抽屉状态卡，v0.4.9）

**GET `/api/web-search`** → `{ configured, provider, keyMasked? }`：联网搜索（Tavily）配置状态；`keyMasked` 仅配置时返回（脱敏形如 `tvly****t123`），永不下发完整 Key。

**POST `/api/web-search`** → 请求 `{ apiKey?: string, provider?: string }` → `{ configured, provider, keyMasked? }`
- `apiKey` 为空 → 删除配置（关闭联网搜索）；非空 → 写入 config.json `webSearch` 字段（落盘持久化）。
- 校验（v0.4.9 代码审查补充）：`apiKey` 非空且 <5 字符 → 400「apiKey 长度不足（≥5 字符）…」（与 saveProvider 一致，防误输短 Key 静默覆盖有效 Key）；`provider` 仅接受 `tavily`，其余 → 400「不支持的搜索服务」。
- 语义：可选增强。未配置时生成管线**完全跳过联网搜索**，AI 按【联网核实协议】在正文标注【待联网核实】并汇总到 `done.needsVerify`；配置后 runGenerate 先自动搜索"公司+岗位"权威来源（Tavily，basic 深度，2 查询），注入上下文【联网搜索资料】区块，搜索失败/无结果均跳过不阻断。
