> 定位：本文档讲解 简历生成助手 的技术架构、核心设计思路与升级路径，回答「为什么这么设计」。
> 配套文档：[docs/contract.md](contract.md)（前后端工程契约，字段/接口/验收）｜[docs/PRD.md](PRD.md)（产品需求）｜[docs/CHANGELOG.md](CHANGELOG.md)（变更留痕）

## 1. 产品与技术概述

**一句话**：本地运行的简历生成 Agent——输入个人背景 + 目标岗位 JD，一键生成面向岗位定制、页面填满、内容真实的简历（HTML / PDF / Word / Markdown 多格式导出）。

| 项 | 定稿（实际实现） |
|---|---|
| 后端 | Python 3.10+ / FastAPI / uvicorn，单进程单任务串行 |
| 前端 | 原生 HTML/CSS/JS（零构建，无框架依赖） |
| 数据 | 本地 JSON 文件（`data/resumes|tasks|photos|cache|calibration.json`） |
| LLM | provider 适配层，OpenAI 兼容接口（默认 DeepSeek），支持多配置 |
| 搜索 | 可选联网搜索（Tavily/Serper），失效降级不阻塞 |
| 运行形态 | 本地单用户、无云服务、无独立 DB、无鉴权 |

设计基线（贯穿全项目）：
- **数据契约驱动**：`app/schemas/` 的 Pydantic 模型即字段契约，前后端共用；
- **真实优先**：数值合理估算、AI 内容来源标记、编辑锁定、导出确认清单；
- **强约束**：板块数量、项目条数、页面填充度均有硬规则，不依赖 LLM 自觉；
- **失败隔离**：单板块失败重试降级，整单继续；仅致命错误置 failed。

## 2. 总体架构

```
┌───────────────────────────── 浏览器（零构建单页面板）────────────────────────────┐
│  form(填写) → validate(预校验/提交关卡) → generate(SSE 进度) → edit(预览编辑锁定) │
│  → adapt(实测/校准) → export(确认清单 + HTML/PDF/Word/Markdown/JSON)             │
└────────────────────────────────────┬─────────────────────────────────────────────┘
                                     │ HTTP + SSE
┌────────────────────────────────────▼─────────────────────────────────────────────┐
│  app/api/            路由层（薄）：resume / upload / generate / skills / adjust …  │
│  app/core/           校验 validation / 规则加载 rules / LLM providers / 错误码     │
│  app/engine/         ★ 生成引擎：analysis → dag 调度 → blocks 生成 → assembly 装配 │
│                       budget 预算校准 / cache 缓存 / prompts 八层组装              │
│  app/search/         联网搜索（api_search，限频 + 降级）                           │
└────────────────────────────────────┬─────────────────────────────────────────────┘
                                     │ OpenAI 兼容
                        ┌────────────▼────────────┐   ┌──────────────┐
                        │  LLM（DeepSeek 等）      │   │ Tavily/Serper │
                        └─────────────────────────┘   └──────────────┘
```

**关键分层原则**：
- 路由层只做参数校验与状态读写，业务全部下沉 engine；
- engine 内「分析 → 调度 → 生成 → 装配」四段解耦，每段可独立演进（升级路径 §5 依据）；
- 模板（`templates/`）、规则（`rules/`）独立于代码，支持热替换与版本化。

## 3. 核心设计思路

### 3.1 数据契约驱动（schemas = 单一事实源）

`app/schemas/`（Pydantic v2）同时承担「数据模型」「字段契约」「输入校验」三重角色：
- 前端按契约渲染表单、后端按契约校验、引擎按契约消费，三者零手写对齐；
- camelCase 命名统一，`CamelModel` 负责蛇形/驼峰转换，避免前后端字段漂移；
- 枚举（PageOption / Density / Criticality / SourceType…）收敛非法输入。

> 设计取舍：不引入独立 ORM/数据库——单用户 + JSON 文件足够，且任何时刻可用任意文本工具直接查看、修正数据，契合「数据不出机、明文可查」的产品承诺。

### 3.2 生成引擎：DAG 分层并行 + 失败隔离（app/engine/dag.py）

```
pending → analyzing(JD 分析 + 缓存 + 可选搜索) → generating → building → done
```

- **两层并行 DAG**：第一层（LAYER1：summary/education/internship/skills/honor）无 JD 依赖，`asyncio.gather` 并行；第二层（LAYER2：projects/skill_extend）依赖共享事实表，串行等待后并行。
- **进度归一化**：`BLOCK_WEIGHTS` 按「本次实际相关板块」重归一化，跳过项（如无实习）不计入分母，进度 0→1 单调。
- **失败隔离**（核心健壮性设计）：单块 LLM 调用失败 → 重试 1 次 → 仍失败输出降级结果 `{"degraded": true}`，整单继续；仅事实表/模板缺失等致命错误才置 `failed`（§5.6）。用户看到的永远是「有结果的单子」而非「半途而废」。
- **终态幂等**：canceled 状态下任何阶段不再推进/覆盖状态。

### 3.3 JD 分析 → 共享事实表（单点事实源）

`JDAnalyzer.analyze()` 将 1~5 套 JD 提炼为 `Factsheet`（direction / coreSkills / jdFocus / projectType / metricStyle / domainTags），所有下游板块（项目、技能、自我评价）只消费这份事实表：
- 避免各板块各自解读 JD 造成口径分裂；
- 缓存复用：`GenCache.jd_key`（JD 内容 + 规则版本哈希），同一 JD 多次生成不重复分析（省 token、结果稳定）；
- **主题一致性**：领域标签共享 ≥1 直接通过；否则 LLM 语义兜底（score ≥0.4），跨领域 → `E_THEME_BLOCK` 拦截，防止「JD 是算法岗、经历全写前端」的错配投递。

### 3.4 Prompt 八层结构与自估协议（app/engine/prompts.py）

每块 Prompt 固定八层：①系统人设 → ②简历数据 → ③JD → ④共享事实表 → ⑤规则与风格 → ⑥输出格式（严格 JSON）→ ⑦预算约束 → ⑧合规边界。

- **自估协议**：每条正文强制输出 `estimatedLines`（1~8），供预算/分页预估使用——这是「页面填满」能在生成期就干预的关键抓手；
- 严格 JSON + 围栏容忍：`extract_json` 剥离 ```json 围栏与前后解释文本，再取首尾大括号，抵御 LLM 输出脏尾巴。

### 3.5 分页模拟与密度自适应（防空白 / 防溢出核心，app/engine/assembly.py）

这是本项目最复杂、迭代最多的模块。核心矛盾：**LLM 输出是黑盒，但简历必须恰好填满目标页数**（一页版 1 页、两页版 2 页）。

三层设计：

1. **参数化排版估算（_LAYOUT）**：把模板 CSS 的真实排版参数全部建模——字号 → 每行字符数、行距 → 行高、页边距 → 可用区域、固定元素（抬头/联系方式/板块标题/水印/安全留白）单独扣除、条目间距 / 列表项间距 / 概述行距 / 技能行距单独计入。
2. **分页模拟（_paginate）**：还原浏览器分页规则——条目 `page-break-inside: avoid` 放不下整块推页，板块标题与首条目 `page-break-after: avoid` 绑定（标题不孤悬页尾），推页空隙计入损耗，从而**估算出真实的空白量**。
3. **双向密度调节（_auto_density）**：目标页数下估算过满 → 降档压缩（compact）；太空 → 升档填充（loose）；末页填充度 <35% 视为太空。全流程自动，无需用户干预。

**校准数据**（从实测回归沉淀）：内容安全系数 `_SAFETY=1.45`、要点换行损耗系数 `_LI_WRAP=1.2`——中文简历中英混排时标点禁行首、西文词不断行使实际行数显著高于理论值，这是早期「估算 2 页但实际溢出 3 页」的根因，通过系数补偿后四轮实测收敛。

### 3.6 数量硬约束（app/core/validation.py + blocks/projects.py）

板块数量不依赖 LLM 自觉，由规则表强制执行：

| 页数 | 无实习 | 1 段实习 | 2 段实习 |
|---|---|---|---|
| 一页 | 2 | 1 | 1 |
| 两页 | 3 | 2 | 1 |

- 规则（用户确认 2026-08-14）：**无实习 2 条 / 有实习 1 条**（一页版）；两页版 0 实习 3 / 1 实习 2 / 2 实习 1；
- 每项目要点数为 STAR 四段硬结构（方案 A 定稿 2026-08-17）：一页恒 4 条 S/T/A/R；两页少项目（≤2）6 条（S/T/A×3/R）；两页多项目（≥3）4 条（S/T/A/R）——由 `bullet_limit` 强制执行，项目必须包含完整 STAR。

### 3.7 真实优先三道防线

| 防线 | 机制 | 实现 |
|---|---|---|
| ① 数值真实 | 引导 LLM 生成「可被面试追问验证」的合理数值，禁止占位符 | Prompt 人设 + 量化风格 |
| ② 来源透明 | 内容标记 `source: polished / ai-created / user-input` + `aiFlag` + 有水印模式页脚声明 | assembly / blocks |
| ③ 编辑锁定 | 用户编辑项 `criticality: critical`，压缩/裁剪绝不命中；导出前强制 AI 内容确认清单 | 前端编辑 + 导出关卡 |

### 3.8 预算校准闭环（app/engine/budget.py）

LLM 自估行数（§3.4）→ 前端实测实际渲染行数 → `record_actual` 落 `data/calibration.json` → 校正系数 = 历史 actual/estimated **中位数**（抗离群）→ 回写下一次预估。这是一个持续自学习的误差修正回路，随使用次数增多，密度估算越准。

### 3.9 缓存与重入（app/engine/cache.py）

- key = SHA256(规范化 JSON) 前 20 位，`canonical_json`（key 排序）保证同内容同哈希；
- 失效策略：规则/prompt 版本变更 → key 变化即天然失效；用户编辑 → 输入哈希变化自动失效；
- `tmp + rename` 原子写，本地单用户场景防半写损坏。

### 3.10 技能分类收敛（app/engine/blocks/skill_extend.py）

LLM 推荐技能时分类可能过碎（单个技能独立成类），后处理 `_coalesce_categories()`：
- 单技能非固定分类并入相近大类（编程语言 → 专业技能，其余 → 工具与框架）；
- 总分类硬约束 3~5 个，超出时保留固定 3 类 + 技能数最多的额外类；
- 语言能力允许单条但必须带等级标注（英语（CET-6））。

### 3.11 规则文件独立于代码（app/core/rules.py）

行业模板库、技能判定、项目映射、JD 主题规则全部下沉 `rules/` JSON：
- 加载时 jsonschema 校验，非法规则直接拒绝（不静默降级）；
- `GET /api/health` 暴露各规则文件版本号；
- 规则版本进入缓存 key 与 JD 分析 key，规则变更自动全量失效——**运营数据与代码解耦**，改规则无需发版。

## 4. 关键运行流程

### 4.1 生成任务状态机

```
pending ─→ analyzing ─→ generating ─→ building ─→ done
   │           │             │             │
   └───── canceled（任何阶段可取消，终态幂等）
   └─ failed（仅致命错误：事实表/模板/全局异常）
```

### 4.2 SSE 事件流与断线回放

- 事件：`task.stage` / `block.progress` / `block.done` / `task.done` / `task.failed`；
- 全部事件持久化到 `task.events`，SSE 断线重连可回放（恢复进度条，不丢状态）；
- `task.done` 直接携带装配好的 HTML 与 config（含 density / contentPlan / blocks 自估基线），前端可即时渲染，无需二次请求。

### 4.3 提交关卡（POST /api/generate）

生成前置四重校验，任一不通过即拦截：JD 分析可用性 → 技能相关性（pass/weak/block 三档）→ 主题一致性 → 数量约束（实习→项目数）。拦截在「花钱调 LLM」之前，避免无效生成。

### 4.4 装配 building（_build → Assembler.render）

1. 各块输出回写 resume（summary/internship/projects/skill/ honor）；
2. `contentPlan` 固化本次详略档与每项目要点数（bulletCountPerProject）；
3. `Assembler.render`：模板占位符替换 → 空区块删除（实习/荣誉未填充整块不输出）→ 照片位 → **密度自适应定档** → 水印注入。

## 5. 升级路径

> 依据：PRD 优先级（P1/P2/P3）+ 代码现状 + MS-Agent 实践经验。按「收益 / 成本」排序。

### 5.1 短期（正确性与体验补强）

| # | 方向 | 动机与建议实现 |
|---|---|---|
| 1 | **密度估算持续校准** | 当前 `_SAFETY` / `_LI_WRAP` 为静态系数；建议把校准闭环（§3.8）从「记录」升级为「自动回写系数」，并按 density 档分桶统计，进一步收敛不同浏览器（Chrome/Edge/Safari 字体回退差异）的渲染偏差 |
| 2 | **PDF 原生导出** | 当前 PDF 依赖浏览器打印（Ctrl+P）；建议引入无头渲染（Playwright/weasyprint）服务端直出 PDF，打通「一键导出 PDF」闭环 |
| 3 | **多 Provider 优先级自动切换** | `core/providers.py` 已支持多配置；补「主 Key 失效 → 自动切备用」运行时切换（PRD US7） |
| 4 | **单条内容重生成增强** | 现有单条重生成基于整块重跑；建议细化为「局部重写 + 上下文锚定」（仅该条目，参照前后文），降 token 且不扰动其他内容 |

### 5.2 中期（能力扩展）

| # | 方向 | 动机与建议实现 |
|---|---|---|
| 5 | **简历库与多份简历管理** | 当前单份简历编辑；建议支持多份简历（不同方向版本）列表管理，JD 定向生成后存档复用 |
| 6 | **插件生态深化** | 已具备插件双层启动机制（R19/R20：OpenCLI / MediaCrawler / Agent-Reach / Tavily）；建议插件化「取材 → 生成 → 审核」三阶段钩子，第三方可注入自定义板块生成器 |
| 7 | **批量投递流水线** | 输入多份 JD → 批量产出多份简历 + 面试材料（对齐 MS-Agent 的 8 份材料输出），形成「简历 + 面试准备」完整求职链路 |
| 8 | **规则文件可视化编辑** | 行业模板/技能/项目规则目前为 JSON；建议设置页可视化编辑并即时校验，降低维护门槛 |

### 5.3 长期（形态演进）

| # | 方向 | 动机与建议实现 |
|---|---|---|
| 9 | **多模态输入** | 对齐 MS-Agent 视觉版：扫描版简历/图片 JD 自动解析（本地离线 OCR 或视觉模型），降低录入成本 |
| 10 | **端到端评测体系** | LLM 输出质量目前靠人工；建议建立「输出 → 规则校验 → 人工评分」回归集，量化 density 收敛率 / 数量约束达标率 / 关键词覆盖率，防止迭代回退 |
| 11 | **并发与任务队列** | 当前单任务串行（设计取舍）；若推广至多用户/批量场景，可引入轻量任务队列（asyncio.Queue + 限流），但需评估是否背离「本地单用户」定位 |
| 12 | **云端多用户/账号体系** | PRD 明确非目标（无云、无账号）；仅当产品转型才需评估——届时数据加密、鉴权、审计需整体设计 |

### 5.4 架构演进注意点

- **adapter 层独立**：contract 规划的 `app/adapter/` 目前内聚在 `assembly.py`（密度定档 + 分页模拟）；当密度逻辑继续膨胀（多档、多模板、校准回写），建议抽出独立 `adapter/` 模块，保持 assembly 只做模板装配；
- **块注册表扩展**：新增板块只需在 `blocks/` 添加生成器 + 注册进 `BLOCK_GENERATORS`/`LAYER` + 补充 `BLOCK_WEIGHTS` 与 `ESTIMATED_KEYS`，扩散点集中在三处，应固化为开发规范；
- **规则版本化发布**：规则文件已是版本化的，建议与 GitHub Release 联动（tag 时校验 schema 并生成规则变更摘要）。

## 6. 已知边界与风险

| 边界 | 现状 | 影响 |
|---|---|---|
| 密度估算依赖浏览器渲染一致性 | 系数按 Chrome 系标定 | 极窄字体环境下可能偏差 ±5%，靠 `_auto_density` 兜底 |
| LLM 输出偶发非 JSON / 截断 | `llm_with_degrade` 重试 1 次后降级 | 极端情况板块内容降级为「（待补充）」，不中断整单 |
| 单任务串行 | 设计取舍（§1） | 并发生成请求会排队 |
| 联网搜索为可选 | Key 未配或失败时降级 | 生成结果缺时效信息，`search_degraded` 标记不阻塞 |
| 错误码集中 | `core/errors.py` 已覆盖客户端（4xxxx）与服务端（5xxxx） | 新增错误需登记，避免码冲突 |
