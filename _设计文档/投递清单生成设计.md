# Q10 投递清单生成设计（生成逻辑 + 数据结构定义）

> 状态：v0.2（2026-08-15，Q10a/b/c/d 已确认）
> 配套：`4_大改造架构设计-v2.0.md` §0.5.3（投递=人工环节）/ §5.3（N9 投递执行）/ §5.5.6（版本注册表）/ §6.1（match_agent 契约）
> 定位：match_agent **只出候选**，用户**终选**——投递清单是大脑在 N9 展示给用户的**结构化推荐岗位清单**，作为用户挑选投递的依据。清单**只推荐、不引导**。

---

## 1. 定位与边界

| 项 | 定义 |
|---|---|
| 生产者 | **大脑节点**（不是 match_agent 内部产物——match_agent 只输出 `match_results` 候选，§6.1） |
| 展示点 | 大脑 N9「投递确认」interrupt 时展示（§0.5.3 / §5.3） |
| 消费方 | ① 用户（查看参考，**自行独立投递**）② prep（只对**已投**岗位生成材料，§0.5.3）③ 大脑报告（只读汇总 tracker 数据） |
| 不做什么 | **不替用户投递**（JobHunter 无代投功能，投递由用户独立完成于系统外）；**不自动写 tracker**（面试跟踪信息由用户手动录入，大脑只读）；不提出投递数量/节奏建议（无上限、无"优先投哪个"引导）；**不参与简历版本绑定**（版本对应在 N4 JS 岗位筛选时已明确，清单继承） |

**边界**：投递清单是"结构化推荐 + 用户挑选状态"的工作台状态。长期看板（已投/约面/结果）由 tracker 维护（§0.6.3 C3）。

## 2. 生成逻辑

### 2.1 生成时机与位置

```
N5 质量判定 pass（或 accept_with_issues 降级）
  → 投递清单生成（大脑节点 · 规则为主，无 LLM 仲裁）
  → N9 投递确认（interrupt：展示清单供用户参考，不自动投递）
  → 用户自行投递（系统外操作）→ 手动录入 interview-tracker
  → prep 按已投岗位生成材料（以用户确认的投递为准）
```

> 与 v2.0 §0.5.3「面试准备的输入是已投递岗位」对齐——投递确认应在 prep 之前。当前 JobMaker 骨架的「定稿确认」在「面试准备」之后，属骨架版简化顺序，Q10 落地时调整。

### 2.2 输入

| 输入 | 来源 | 用途 |
|---|---|---|
| `accepted` 的 match_results | N5 收录（`final_score ≥ accept`，H1-H6 已裁决） | 候选池 |
| match_results 内嵌 `resumeVer` | **N4 JS 岗位筛选时已明确**（§2.4） | 版本对应（清单只继承） |
| profile | 画像（城市/方向等） | 仅作展示上下文，不做二次过滤（N5 已裁决） |

### 2.3 处理流程（规则为主，LLM 仅润色理由）

```
accepted 候选池
  → ① 排序     final_score 降序（主）；同分按时效新（fresh_days 内）优先（次）
  → ② 展示分档  按分数分档仅作视觉分组，纯信息不构成投递建议：
               P0: final_score ≥ 90
               P1: 80 ≤ final_score < 90
               P2: accepted 且 < 80
  → ③ 理由     聚合 reasons（规则原因）+ 时效/企业档标注；
               LLM 润色为 ≤50 字投递理由（LLM 异常 → 用 reasons 摘要，不阻塞）
  → ④ 汇总     summary：总数 / 分档计数 / 渠道计数 / 版本计数
```

**明确排除**：无数量上限、无截断、无"P0 优先投"类引导——用户自己决定投哪些、何时投（Q10c 确认）。

**LLM 参与度**：仅 ③ 理由润色（可降级）。排序/分档全部规则确定性执行——投递清单是给用户看的"推荐"，N5 已做判定，清单阶段不引入第二次不确定判定。

### 2.4 岗位 ↔ 简历版本对应（N4 明确，清单继承）

> Q10d 确认：投递清单**不参与**版本决策；版本对应关系在 **JS 岗位筛选时**（N4 match_agent）明确。

```
N4 JS 岗位筛选（输入含简历版本线信息）
  → 每个收录岗位绑定 resumeVer：基于哪个版本简历筛出的该岗位
  → 无匹配版本线 → "pending_version"（N4 阶段标记，§5.5.6 不猜，用户后续选版）
  → match_results 每项内嵌 resumeVer（§6.1 契约扩展）
投递清单生成时直接继承，不做版本匹配/重绑定
```

## 3. 数据结构定义

### 3.1 大脑 State 字段（JobHunterState 新增）

```python
submission_plan: Dict[str, Any]   # 投递清单（N9 前置生成，interrupt 展示）
```

### 3.2 SubmissionPlan（顶层）

```jsonc
{
  "submission_plan": {
    "generated_at": "2026-08-15T10:00:00+08:00",
    "status": "pending_review",          // pending_review → confirmed / cancelled
    "items": [ SubmissionItem, ... ],    // 按 final_score 降序（同分时效优先）
    "summary": {
      "total": 10,
      "by_tier": { "P0": 3, "P1": 5, "P2": 2 },
      "by_channel": { "招聘平台": 6, "官网": 3, "社区": 1 },
      "by_resumeVer": { "line-aiinfra-v2": 8, "pending_version": 2 }
    }
  }
}
```

### 3.3 SubmissionItem（清单项）

```jsonc
{
  "job_id": "J-007",
  "title": "大模型推理优化工程师",
  "company": "示例公司",
  "city": "上海",
  "channel": "招聘平台",                  // 枚举：招聘平台 / 官网 / 社区（沿用 §2.3）
  "source_url": "https://...",
  "final_score": 92,                      // N5 判定后分数
  "fits": { "jd_fit": 0.8, "quality": 0.6 },   // LLM 软性维度（仅展示，§1.6）
  "resumeVer": "line-aiinfra-v2",         // ★ 继承自 N4 match_results（清单不参与版本决策）
  "tier": "P0",                           // 展示分档（纯信息，无投递建议语义）
  "reason": "强匹配：技能线全覆盖 + 同城 + 时效新",   // ≤50 字（LLM 润色，可降级）
  "reasons": ["技能匹配度高", "同城"],      // 规则原因摘要（降级时即投递理由）
  "user_action": "suggested",             // 用户参考标注：suggested → skipped（§3.5，不驱动投递）
  "applied_at": null
}
```

### 3.4 枚举总表

| 字段 | 枚举 | 说明 |
|---|---|---|
| `tier` | `P0 / P1 / P2` | **展示分档**（视觉分组，不构成投递建议，§2.3②） |
| `user_action` | `suggested / skipped`（可选标注） | 用户参考标注，不驱动投递（§3.5） |
| `channel` | `招聘平台 / 官网 / 社区` | 沿用 match_agent 渠道枚举 |
| `resumeVer` | `line-<方向>-v<N>` / `pending_version` | 版本 ID（D11）；**N4 绑定，清单继承** |
| `status`（plan 级） | `pending_review / confirmed / cancelled` | 清单生命周期 |

### 3.5 用户挑选标注（清单上的参考标注，不自动写 tracker）

```
suggested ──用户标注──→ skipped（参考清单上标记跳过，可带 reason）
    └──用户自行投递（系统外）→ 在 interview-tracker 手动录入
```

- `user_action` 只是清单上的**用户参考标注**（可选），不驱动任何系统投递动作
- 投递进度以 tracker 中**用户手动录入**的记录为准；大脑不自动写 tracker
- `applied_at`：清单项被用户标注"已投"的时间（用户反馈/标注，非系统检测）

### 3.6 与 tracker 的关系（用户手动录入，大脑只读）

```
用户投递完成（系统外：BOSS/官网/内推等）
  → 用户在 interview-tracker 手动录入投递/面试记录
  → 大脑只读汇总 tracker 数据（投递看板/总报告），不自动写入
```

> 纠偏（2026-08-15）：JobHunter **无替用户投递功能**；投递由用户独立完成；tracker 信息由用户手动录入。原"大脑确认后写回 tracker"设计作废。
